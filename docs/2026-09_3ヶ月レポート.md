## 0. 結論の要約

3ヶ月で作ったものは、**予算の消化ペースから年度末の着地を予測するシステム**です。
実データで最初から最後まで動き、GitHubに全部入っています。

ただし**最も重要な発見は、予測の数字ではありませんでした。**

3案件すべてで、**予算の主要費目が仕訳帳に1行も存在しない**ことが判明しました。
P3では人件費と支援金で予算の73%、P2では7費目すべてが実績ゼロです。つまり
「消化率10%」という数字は、そもそも分子が欠けた状態で計算されています。

このシステムがいま実証できている価値は、**予測の精度ではなく、予測しようとした
結果としてデータの欠損を発見したこと**です。ここは目的地の再設定に関わると思うので、
最初に書いておきます。

### 【2026-09-07 追記】設計の中核に初めて数字がついた

9/4に検証の仕組みを作り、**「3つの視点に分ける」という設計が機能している証拠**が
出ました。実データの答え合わせではありません（年度末実績がまだ無いため）が、
**機械が正しく推論できるか**は測れるようにしました。

| シナリオ | 仕訳帳が実態を覆う割合 | 3体の割れ幅 | 予測誤差 | 単純外挿 |
|---|---|---|---|---|
| 順調 | 100% | **0.110**（収束） | **3.8%** | 9.1% |
| 仕訳漏れ | 33% | **0.875**（要確認） | **17.0%** | 69.7% |

重要なのは誤差ではなく、**割れ幅が8倍違う**ことです。3体の意見の食い違いは
どの局面でも大きいのではなく、**データが実態を覆えていないときだけ広がりました。**
つまり——

> **予測が外れているときに、「この数字は信用するな」と自動的に言えている。**

外れること自体は避けられません。避けたいのは**外れているのに自信満々**であることで、
そこは制御できていると確認できました。

## 2. 最大の発見：予測ではなく、データの欠損

8/19と9/2の実行で、3視点が254万円ぶん割れました。原因を追った結果です。

### P3（財団案件・2025年度・6月末時点）

- 予算 4,237,552円 ／ 実績 423,866円
- 経過率 25% に対し 消化率 10%

| 視点 | 着地見込み | 予算比 |
|---|---|---|
| 実績AG | 1,695,464円 | 40.0% |
| 制約AG | 3,480,642円 | 82.1% |
| 計画AG | 4,237,552円 | 100.0% |

**乖離度 0.730**（閾値0.3）。Pythonによる検算では3体とも算数に誤りなし。
**全員が正しい計算をして、それでも254万円ずれた。**

原因はこうでした。

| 予算にある費目 | 予算額 | 仕訳帳での実績 |
|---|---|---|
| 人件費 | 1,878,320円（予算の46%） | **該当取引 0件** |
| 支援金 | 1,200,000円（予算の28%） | **0円** |
| **合計** | **予算の約73%** | **1行も存在しない** |

つまり実績AGは、**予算の約3割しか含まない母集団**を年換算していました。算数は
正しいのに、事業全体の着地推定には使えない値です。計画AGの100%も「予算額を
超えない」という制約による定義上の張り付きで、上限であって予測ではありません。

### 同じパターンが3案件すべてに

| 案件 | 予算 | 実績 | 状況 |
|---|---|---|---|
| P1 | 未確定 | 15,687円（広告宣伝費のみ） | 主要費目なし |
| P2 | 2,398,000円 | 48,318円（支払手数料のみ） | **予算7費目すべてに対し実績0円** |
| P3 | 4,237,552円 | 423,866円 | 人件費・支援金が0円 |

**P3固有の問題ではありません。** 経理の運用そのものに起因している可能性が高い。

### 経理に確認したいこと（最優先）

> **人件費と支援金は、まだ執行されていないのか。
> それとも執行済みだが、この仕訳帳に載らない経路で処理されているのか。**

- **未執行なら** → 着地は約348万円（予算の82%）
- **別経路で処理済みなら** → 「消化率10%」という数字そのものが誤り

**この1点で解釈が正反対になります。** ここが未確定のまま出す予測は、どの数字で
あっても根拠が弱いままです。

### この発見の意味

**1体のAIに「着地はいくら？」と聞いていたら、「40%で着地します」と答えて
終わっていました。** 数字は返ってくるし、それらしく見える。しかしその数字が
予算の3割しか見ていないことに、誰も気づけません。

材料を分けたことで3体の答えが噛み合わなくなり、噛み合わない理由を追ったら
データの穴に行き着いた——これが3視点構成の実証された効果です。

## 3. 現在の設計

### 全体の流れ

```
生データ ─→ ①門番(Python) ─→ ②収集AG ─→ ③証拠分割(Python)
        ─→ ④3視点AG(並列・独立) ─→ ⑤集計(Python) ─→ ⑥調整AI ─→ ⑦ダッシュボード
```

**PythonとAIが交互に並んでいるのは意図的です。** 数を数える・切り分ける・検算する
といった**間違えてはいけない確定作業はPython**、**意味を読み取る作業だけAI**に
任せています。どちらも「できてしまう」のですが、できることと任せてよいことは違います。

### 設計上の絶対ルール（4つ）

1. **3視点AGを互いに議論させない。** 討論型は単純なCoTにすら負ける
2. **3視点に同じ証拠を配らない。** 同一証拠は同調を招く。分割は**物理的に**行う。
   プロンプトで「見ないでください」と頼む形は、ファイルにあれば読めるので無意味
3. **数値はPython、解釈はLLM。** 各AGの算数はPythonが検算する
4. **門番はPython。** LLMマスキングは原理的に破綻する

### 門番（マスキング）の設計

**ホワイトリスト方式**です。許可した業務語（339語）で完全に分解できる語だけを通し、
それ以外の漢字・カタカナ・英字の連なりは一律で伏字化します。

**逆向き（危ない語を列挙して塞ぐブロックリスト方式）は原理的に漏れます。**
列挙し忘れたものが必ず出るからです。法人格（「株式会社」等）を手がかりにすると、
法人格を含まないブランド名が網にかからない。氏名にいたっては規則性がなく
列挙のしようがありません。

実装上の要点が3つあります。

- **部分一致で通さない。** 「〈地名〉交通費」は「交通費」を含むが地名は許可語ではない。
  **語が許可語だけで完全に分解できる場合のみ通す**
- **数量は落とさない。** 機密なのは単価であって数量ではない。「0.5日/月×12か月」の
  0.5や12は誰の情報でもなく、制約AGが「経過した月の分は後から積めない」と判断する
  ための中核データ。閾値1,000円で単価と数量を分けている
- **伏字は元と同じ文字数にする。** `pdftotext -layout` は空白で列位置を表すため、
  可変長の伏字だと桁が崩れ、どの数値が単価列でどれが金額列か判別できなくなる

### 検査（本文を読まずに安全性を確認する）

マスク結果の確認に人やLLMが本文を読むと、漏れていた場合に「確認のために漏らす」
ことになります。そこで**検査は集計値だけを返す**設計にしました。

| 観点 | 内容 | 現在の結果 |
|---|---|---|
| ① | 未許可語が残っていないか | 5ファイル全て **0** |
| ② | 単価語のある行に生の金額が残っていないか | 全て **0** |
| ③ | 敬称（様・御中）の直前が伏字か | 全て **0** |
| ④ | 分析に必要な情報が残っているか | 金額4〜35件が保持 |

**①②③がすべて0でなければ社外に出しません。**

### PDFの扱い（8/19〜9/2に解決）

当初「PDFは門番を通せない」と結論していましたが、**これは不正確でした。**
Pythonが苦手なのは*表の意味を理解して構造化すること*であって、*テキストを
取り出すこと*ではありません。分業すれば扱えます。

```
pdftotext(ローカル) → Python門番(ローカル) → ここで初めてLLMが構造化
```

見積書PDF5件すべてで成功し、**手作業で書き起こした版と主要6項目が完全一致**
しました（事業費1,974,000／人件費・管理費1,878,320／小計3,852,320／
一般管理費385,232／税抜4,237,552／税込4,661,307）。手作業では128,000円の
転記ミスが発生していたので、**精度は自動のほうが上**です。

ただし**CSVで頂けるほうが精度は高くなります。** PDFはテキスト抽出時に列の対応が
崩れるため、明細と大項目の突合が取れない箇所が残ります。テンプレートを用意しました。

### エージェントの実体

エージェントは `.claude/agents/*.md` という**職務記述書**です。知能はClaude側に
あり、mdは役割の定義だけを持ちます。システム全体で約470行のMarkdownです。

この形にした効果が3つあります。

1. **アカウントが変わっても移植作業ゼロで動く**（gitに入っている）
2. **非エンジニアでも読めて直せる**
3. **エージェントが状態を持たないので過去時点を正確に再現できる＝バックテストが成立する**

なお**調整AIだけは定義ファイルがありません。** Claude Codeのメインセッション自身が
担うためで、振る舞いは `SKILL.md`（手順書）に書いてあります。

## 4. できていること / できていないこと

### できていること

| 機能 | 検証の中身 |
|---|---|
| 門番（CSV・PDF両対応） | 8ファイル。検査①②③すべて0 |
| PDF自動取り込み | 手作業の書き起こしと主要6項目が完全一致 |
| 予算と実績の対応づけ | 対応できない箇所を自分で `uncertain` に記録できる |
| 証拠の物理分割 | 実績側に予算額が混入しないことを検査済み |
| 3視点が本当に割れる | 乖離度0.730。同調していない |
| 数値の検算 | 3体とも算数の整合に問題なし |
| 統合と原因の特定 | 割れの原因がデータの穴だと突き止めた |
| ダッシュボード | JSONを読んで表示。LLMを呼ばない |
| 引き継ぎ | mdファイル＋git |
| 予測の台帳 | 金額入りは社内、比率のみgit追跡 |

### できていないこと

**最大の穴：実データでの答え合わせを一度もしていない。**

9/4の検証で**機械が正しく推論できること**は確認しました（§0の追記）。しかし
それは人工的に作ったシナリオでの話で、**この組織の予算執行の癖に当たるか**は
まだ分かりません。この2つは別物なので、混ぜないよう注意しています。

- ✅ **測れたこと** — 壊れないか／判定の向きが合っているか／
  **割れ幅が本当の不確実性と連動しているか**／データ欠損を検出できるか
- ❌ **まだ測れていないこと** — **この組織で当たるか**

なお、ダミーデータに合わせて閾値やプロンプトを調整することは意図的に禁じています。
それをやると「作者の想像によく当たるAI」ができあがり、**測定値だけが上がって
実際は何も良くなりません。** 当たっているように見えるぶん、たちが悪い。

台帳（ledger.py）を9/2に実装したので受け皿はできています。比較基準は**季節ナイーブ
（実績累計÷経過率）**とし、これに勝てないなら3体を並べる意味がない、という判定に
してあります。

**手持ちのデータは2025年度で、年度はもう終わっています。**
**年度末の確定実績を頂ければ、8/19と9/2の予測をそのまま答え合わせできます。**
これが埋まれば「この組織で当たるか」も測れるようになります。

その他：

- **読めないデータ形式** — スキャンPDF（画像）、Excel、Word。OCRの `tesseract` は
  導入済みなので繋ぐだけではある
- **P1の予算が未確定** — 仕訳帳はあるが対応する見積書PDFが特定できていない
  （推測での紐づけはしていません）
- **自動実行できない** — 人間がClaude Codeに話しかけるのが起点。
  無課金と引き換えの意図的な代償。必要になればAgent SDKかManaged Agentsへ移行可能
- **旧エージェント3体が残っている** — 置き換え済みだが削除許可待ち

## 5. 目的地の再設定に関わる論点

石川さんから「目的地が変更になる可能性もある」とのお話がありましたので、
判断材料になりそうな点を挙げます。

### 論点A：このシステムの実証された価値は「予測」ではなく「診断」だった

3ヶ月で最も価値を出したのは、**予算の73%が仕訳帳に無いという発見**です。

**【09-07 更新】この論点は、9/4の検証で半分だけ変わりました。**

「3体に分けると精度が上がる」という中核の主張には、**初めて数字がつきました**
（単純外挿に対し誤差3.8% vs 9.1%、17.0% vs 69.7%）。つまり予測機能そのものは
「未証明」ではなくなっています。

ただし**実証の順序は変わっていません。** 先に確かめられたのは
「**データが足りているかを見抜く能力**」のほうで、予測の当たり具合は
実データではまだ測れていない。この構造は変わっていません。

したがって選択肢はこうなります。

| 目的地 | いまの完成度 | 必要なもの |
|---|---|---|
| **年度末の着地を当てる** | 機械は動くと確認済み。組織への当てはまりは未検証 | **年度末の確定実績1回** |
| **経理データが使える状態か検査する** | **すでに実証済み**。3案件で欠損を検出 | 追加検証は不要 |

**両方を同時に狙えます。** 同じパイプラインの出力の、どちらを主役にするかの
違いでしかありません。ただ「まず何で価値を示すか」は決めておきたいところです。

### 論点B：「AIにこだわらず手作業でも良い」への3ヶ月後の回答

7/21に石川さんから頂いた指摘への、現時点での回答です。

- **残額と消化率は確かに引き算です。AIは要りません。**
- **AIが必要なのはその先**——「15ポイントの遅れは巻き返せる程度なのか、
  もう使い切れないことが確定しているのか」の判断です
- そして実際にAIが出した価値は、その判断ですらなく、**判断しようとした結果として
  データの欠損を検出したこと**でした

手作業でも残額は出せますが、**3人分の異なる視点で照合して食い違いを検出する**のは、
手作業では現実的でないと考えています。

### 論点C：ローカルLLMの要否

8/26の打ち合わせで「ローカルLLMを用いたマスキング手法を調査・検討」がタスクとして
残っていますが、**現状の門番はローカルLLMではなくPythonです。** これは意図的な選択です。

| | ローカルLLM | Python門番（実装済み） |
|---|---|---|
| 確実性 | 確率的。一定確率で漏れる | **決定論的。同じ入力なら必ず同じ出力** |
| 監査 | 何を落としたか説明しにくい | **伏字件数・検算通過率を数値で出せる** |
| 検証 | 出力の確認に人が読む必要 | **本文を見ずに判定できる** |
| 環境 | モデル導入・保守が必要 | **追加インストール不要** |

石川さんの関心は「外部流出を防ぐこと」であり、手段がローカルLLMである必要は
ないはずです。むしろ**Pythonのほうが強い保証を出せます**——「AIがちゃんとマスク
してくれたはず」ではなく「規則どおりに落ちたことを数値で示せる」ので。

ただしローカルLLMが有効な場面もあります。①スキャンPDFのOCR、②過剰マスクの
是正（意味を見て人名と業務語を区別できる）。**置き換えではなく層として足す**なら
筋が通ります。ご相談させてください。

### 論点D：一緒に手を動かす時期に入るなら

石川さんが構築中のエージェントと合流する形になると理解しています。接続点として
使えそうなものを挙げます。

- **門番（masking.py / pdf_extract.py / verify_mask.py）は単体で切り出せます。**
  財務予測に依存しておらず、「社外APIへ出す前に個人情報を落とす」汎用の道具です
- **予算CSVテンプレートは共通フォーマットの候補**になります
- **エージェント定義がmdファイルなので、そのまま読んで使えます**

## 6. ナレッジの排出方法について（ご相談）

「今後に向けてその排出方法も議論したい」「専用アカウントを作り相互にナレッジを
放り込む」というお話について、こちらの現状と提案です。

### 現状の排出の仕組み

意図的に3層に分けてあります。

| 層 | 中身 | 置き場 | 公開可否 |
|---|---|---|---|
| 設計 | エージェント定義・手順書 | `.claude/` (git) | 可 |
| 経緯 | 判断と理由、失敗の記録 | `index.html` / `CLAUDE.md` (git) | 可 |
| 実データ | 生データ・マスク結果・予測の実額 | ローカルのみ (gitignore) | **不可** |

**「なぜそうしたか」をコミットメッセージとコード内コメントに書く**運用にしています。
実装だけ見ても分からない判断——ブロックリストをやめた理由、実績スライスから
予算額を落とす理由など——が、あとから読めるようにしてあります。

### 提案

**① 排出は自動生成にする**

この文書自体、対話履歴とgit履歴からAIに出力させたものです。手作りしていません。
同じ形で**月次または打ち合わせ前に自動生成**できます。石川さんのご要望どおり
「出せるだけ出す」形なので、整形コストがゼロです。

**② 共有アカウントに置くものと置かないものを最初に決める**

相互にナレッジを放り込む形にするなら、**実データを置かない線引きだけは最初に
合意しておきたい**です。いま `agent/output/` `agent/masked/` `data/` を
gitignoreにしている理由がそこにあります。共有先が増えると、この線が曖昧になった
瞬間に漏れます。

具体的には「**マスク済みでも実データ由来のものは共有アカウントに置かない。
設計・手順・比率だけを置く**」を提案します。

**③ 形式はMarkdownのプレーンテキストで揃える**

石川さん側のエージェントに食わせるとのことなので、装飾のないMarkdownが最適です。
HTMLは人が読む用、Markdownは機械が読む用、と分けます。
